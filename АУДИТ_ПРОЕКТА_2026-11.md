## 1. Блокеры: риск потери данных

### 1.1. Восстановление бэкапа принимает пустой файл и стирает всё (P0)

`frontend/src/utils/restoreBackup.ts:50-75` проверяет только `if (!backup.version)`. Файл `{"version":"1.0"}` проходит валидацию. RPC `restore_user_backup` (`supabase/migrations/20250108_restore_user_backup.sql:17-31`) удаляет все таблицы пользователя и вставляет то, что есть в JSON — то есть **ничего**. Пользователь видит «Бэкап восстановлен», данных больше нет.

Дополнительно: подтверждение показывается **до** выбора файла (`frontend/src/pages/ReportsPage.tsx:131-167`), превью содержимого нет.

**Исправить:**
- требовать `exportedAt`, `version` из белого списка и хотя бы одну непустую таблицу;
- показывать превью: дата бэкапа, количество счетов/операций/долгов;
- автоматический снапшот текущих данных перед восстановлением;
- в SQL — сверять `p_backup->>'version'` и падать на пустом наборе.

### 1.2. Клиентский fallback восстановления неатомарен (P0)

`restoreBackup.ts:139-172, 214-261`: при недоступности RPC сначала вызывается `clearUserData()` (удаляет всё), потом вставка по таблицам. Если вставка падает на середине (несовместимая версия, кривая строка, таймаут) — данные уже удалены, отката нет. RPC-путь атомарен (plpgsql = транзакция), клиентский — нет.

**Исправить:** либо запретить клиентский fallback без предварительного снапшота, либо обернуть в «сначала загрузить во временные таблицы, потом одной транзакцией заменить».

### 1.3. Экспорт бэкапа молча обрезается (P0/P1)

`frontend/src/api/supabase.ts:1187-1211`: 8 таблиц читаются `select('*')` без пагинации. PostgREST отдаёт не больше `Max Rows` (по умолчанию в Supabase — **1000 строк на запрос**). Всё, что больше, в бэкап не попадает — и об этом ни слова. При 3–4 тысячах операций бэкап уже неполный.

*Требует проверки:* фактическое значение Max Rows в проекте Supabase.

**Исправить:** пагинация по `range()` до конца, счётчик строк в превью, прогресс; при экспорте показывать «N операций выгружено».

### 1.4. Долги разных валют сливаются в один (P0)

`supabase/migrations/20250115_debt_initial_entry.sql:115-131`: поиск «существующего» долга идёт по `user_id + contact_id + type + status`, **без валюты**. Есть «я должен Ивану $100», создаём «я должен 50 000 ₸» — сумма прибавляется к USD-долгу. Остаток, статистика, бюджет и история дальше живут в валюте, которой не существует.

**Исправить:** добавить `AND d.currency = upper(create_debt.currency)`; при несовпадении создавать отдельный долг.

## 9. Архитектура и производительность

1. **Один чанк 1.28 МБ (353 КБ gzip).** Нет `React.lazy` по маршрутам и `manualChunks`; Recharts и все страницы грузятся сразу. На среднем мобильном интернете это 3–6 секунд до интерактива.
2. **N+1 в счетах:** `accounts.getAll` делает отдельный RPC `get_account_balance` на каждый счёт (`supabase.ts:482-500`). 10 счетов = 11 запросов.
3. **Тяжёлые агрегаты:** `get_summary` — цикл по строкам вместо одного `GROUP BY`; `get_balance_history` — `SUM` на каждый день в цикле; `getAllInRange` — до 5000 полных строк с join'ами на клиент.
4. **`transfers.getAll`** выгружает всю таблицу и пагинирует на клиенте.
5. **Ре-сидинг категорий:** `ensureProfileForUser` при каждом старте/логине: если `count(categories) === 0` → `init_system_categories`. Пользователь, удаливший все категории, получает обратно ~9 системных.
6. **Процесс миграций:** 24 SQL-файла, накатываются вручную в SQL Editor; нет CLI-миграций, нет истории применённого, нет откатов.
7. **Нет тестов и CI:** ни одного unit/e2e теста; сборка в Vercel есть, проверок нет.
8. **Дубли логики:** zod-схемы пароля в 4 файлах, `toSnakeCase`-маппинг вручную, «валюта по умолчанию KZT» в 6 местах.

## 10. Что сделано хорошо

Чтобы не выглядело как «всё плохо» — это действительно сильные места:

- **RLS** включён на всех таблицах, политики по `auth.uid()=user_id`, `WITH CHECK` для UPDATE; `delete_own_account` реально вычищает данные каскадами.
- **Транзакционность переводов:** `create_transfer` — один RPC, обе проводки в одной транзакции; `update_transfer` = cancel+create с откатом; отмена ищет проводки по тегу `tid:<uuid>`.
- **Долги:** знаки (погашение iOwe → расход, owedToMe → доход) верны; частичное погашение и пересчёт статусов в одной RPC; initial-запись защищена от удаления.
- **Даты:** приём «полдень локального дня» + `lt(следующий день)` — день не съезжает, конец периода включён.
- **Безопасность фронта:** нет `dangerouslySetInnerHTML`, нет `service_role`, `postgrestFilter.ts` экранирует `% _ \ " ,` и валидирует UUID — фильтр-инъекций нет.
- **PWA:** SW не регистрируется в APK (правильно), Supabase — `NetworkOnly`, `/sw.js` с `no-cache`, `navigateFallback`; тема без FOUC (инлайн-скрипт в `index.html`).
- **Android:** UA чистится и в `MainActivity`, и в `main.tsx`; сборка падает без env — APK не соберётся «немым»; `assertSupabaseEnv` ловит кириллицу в URL.
- **Обработка ошибок в мутациях:** везде toast + `loading`/`disabled` на кнопках, двойной клик погашен.
- **Пустые состояния** есть на всех списках и графиках.

## 11. Предложения по продукту

Отсортировано по «эффект / трудозатраты».

### Сначала — то, что чинит доверие к цифрам

1. **Одна валюта на профиль или честная мультивалютность.** Сейчас можно завести счёт в USD и KZT, а все агрегаты складывают числа. Вариант А (быстро): считать итоги только по валюте профиля, остальные счета показывать отдельным блоком. Вариант Б: курсы + конвертация в агрегатах и переводах.
2. **Автопланировщик.** `pg_cron` раз в час (или Edge Function по расписанию) + `process_scheduled_transactions` при старте приложения; идемпотентность (`SELECT ... FOR UPDATE`, уникальность `scheduled_id + period_date`). Иначе «Скоро к оплате» — просто список.
3. **Бэкап, которому можно верить:** пагинация экспорта, снапшот перед восстановлением, превью и проверка целостности, версия схемы, кнопка «Скачать CSV».
4. **Пагинация и серверный поиск** операций и переводов; в шапке «показано 50 из 1 214».
5. **Инвалидация кэша одним хелпером** после любой денежной операции.

### Ежедневный опыт

6. **Быстрый ввод в 3 касания:** FAB на всех экранах, калькулятор в поле суммы («1200+350», «-10%»), чипы частых категорий, «Сохранить и добавить ещё», шаблоны операций (кофе, такси, аренда).
7. **Мобильный дашборд:** компактные KPI-карточки (доход/расход/остаток), «Сегодня», «До конца месяца», виджет «Скоро к оплате» и прогноз баланса с учётом scheduled.
8. **Бюджеты:** таблица `budgets` (категория, месяц, лимит) + прогресс-бар «план/факт» на дашборде и в отчётах — самый ожидаемый функционал для «финансового учёта».
9. **Офлайн-режим:** `persistQueryClient` в IndexedDB + очередь мутаций с idempotency-key + баннер «нет сети». Для метро/поездок это решающее.
10. **Напоминания:** локальные уведомления по `scheduled_transactions` и `debts.reminder_days` (в PWA — Web Push, в APK — `@capacitor/local-notifications`); поле уже есть в БД, но не используется.
11. **Биометрия/лок:** Face ID/Touch ID в APK, WebAuthn в PWA, скрытие сумм в списке задач.

### Долги, отчёты, планировщик

12. **Долги:** быстрые кнопки 25/50/100 %, «простить остаток» вместо ошибки переплаты, группировка «кто кому и сколько» по контактам, авто-обновление `overdue`.
13. **Отчёты:** сохранённые фильтры (период + счета), CSV вместо заглушек, сравнение категорий с прошлым периодом, роллап подкатегорий, PDF позже.
14. **Планировщик:** «Пропустить платёж» с записью в историю, «Выполнить задним числом», история выполнений, массовые действия.

### Качество и инфраструктура

15. **Тесты:** Vitest на `utils` (даты, деньги, долги, бэкап) + Playwright smoke на 10 маршрутов + pgTAP на RPC долгов/переводов. Сейчас регрессии ловятся только руками.
16. **Code-splitting:** `React.lazy` по страницам + `manualChunks` (react, supabase, recharts) — минус ~40 % первого бандла.
17. **Версионировать `android/`** (без `build/`, `local.properties`, ключей) и добавить `allowBackup=false`.
18. **Иконки PWA + iOS-мета** (`apple-touch-icon`, `apple-mobile-web-app-*`, баннер «На экран Домой»).

## 14. Итог

Проект зрелый: продумана модель данных, RLS, транзакционная логика переводов и долгов, аккуратные мелочи вроде «полудня» для дат и экранирования PostgREST-фильтров. Сборка проходит, типы сходятся, публичные экраны рендерятся без ошибок.

Главные риски — **не в вёрстке, а в доверии к цифрам и сохранности данных**: бэкап может быть неполным или «успешно» стереть всё, долги смешивают валюты, агрегаты складывают разные валюты, операции показывают только 50 строк, а планировщик не исполняется сам. Если закрыть блок «Спринт 0» и пункты 1–5 из «Спринта 1», приложением можно пользоваться без страха потерять историю.
